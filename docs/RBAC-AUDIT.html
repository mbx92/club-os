Security & Access-Control Audit

RBAC Audit — Club OS
(Gym + Restaurant SaaS)

Date: 2026-07-07

Scope: packages/backend (Express/Sequelize) and packages/frontend (Vue 3 / Pinia / vue-router), with focus on the newly-added Batal Transaksi (void/cancel transaction) feature.

Method: full static review of every route file + the RBAC engine, plus a real, executable Jest test suite run directly against the RBAC code (no mocks, no guessing).

Companion document: docs/RBAC-AUDIT.md

1. Executive Summary

The system has a genuinely coherent RBAC design at its core: a single can(user, action, subject) engine on the backend, a route→subject map, and a mirrored menuAccess system on the frontend. That foundation is sound. This audit found 14 findings, including one Critical cross-tenant privilege-escalation bug and a High-severity gap directly affecting the void/cancel-transaction feature built in this session.

Critical RBAC-01 Roles are global — any tenant Admin/Owner can edit or delete any role, including other tenants' custom roles

Area: Backend / multi-tenancy

src/models/role.js src/migrations/20250923014850-create-role.js src/controllers/core/system/permissionController.js src/routes/core/system/permission.routes.js src/middlewares/permissionMiddleware.js 

// middlewares/permissionMiddleware.js
if (req.user.isSuperAdmin) return next();
if (isTenantAdmin(req.user)) return next();   // admin/owner bypass ALL checks

// models/role.js
name: { type: DataTypes.STRING, allowNull: false, unique: true }   // globally unique, no tenantId

// controllers/.../permissionController.js
const role = await Role.findByPk(id);   // no tenantId filter, anywhere

Impact: The Roles table has no tenantId; every tenant's "cashier" user points at the exact same database row. authorize('update','Role') lets through any tenant Admin/Owner, and the controllers never scope by tenant. Concretely:

  • A tenant's own Admin, using the normal Settings → Roles screen, can call PATCH /permissions/roles/:id/permissions for any role ID on the platform, including another tenant's.
  • Granting cashier full {"*":["*"]} access instantly elevates every cashier on every tenant — one click, whole-platform blast radius.
  • Deleting/renaming a shared system role breaks login/menus for every tenant using it.
  • createRole enforces a globally unique name, so tenants share one namespace of custom role names.

Fix:

  1. Add nullable tenantId to Roles (null = system default, non-null = tenant-owned custom role); change uniqueness to (name, tenantId).
  2. Scope every controller query by tenantId (404, not 403, on cross-tenant access, to avoid leaking existence).
  3. Only Super Admin may mutate rows where tenantId IS NULL; tenant Admins may only edit their own tenant's cloned/custom roles.
  4. Add an integration test asserting cross-tenant role access returns 404.
High RBAC-02 Voiding a transaction reuses the generic Transaction:update permission

Area: Backend — directly affects the "Batal Transaksi" feature built this session.

routes/gym/transaction/transaction.routes.js:90-94 modules/restaurant/routes/order.routes.js:192-194 utils/defaultRolePermissions.js 

// Gym
router.post('/:id/cancel', authorize('update', 'Transaction'), requireFeature('refunds'), transactionController.cancelTransaction);

// Restaurant — used by the void feature to set status:'cancelled'
router.put('/:id/status', authorize('update', 'Transaction'), orderController.updateOrderStatus);

// defaultRolePermissions.js — these roles already have Transaction:update
cashier: { Transaction: ALL }
staff:   { Transaction: READ_CREATE_UPDATE }
kitchen: { Transaction: ['read','update'] }
waiter:  { Transaction: READ_CREATE_UPDATE }

Impact: "Move an order from pending to preparing" and "permanently void a paid transaction" check the exact same permission. By default, waiter, kitchen, and staff — day-to-day operational roles — can already call both void endpoints. The restaurant path also has no requireFeature('refunds') gate, unlike Gym. The frontend's VoidTransactionPanel.vue shows the "Batal" button purely based on transaction status, with zero client-side permission check.

Fix:

  1. Introduce a distinct cancel action for Transaction; grant it only to admin/owner/manager (+cashier if desired) by default.
  2. Enforce it on the Gym cancel route and special-case the restaurant status route when transitioning a completed/paid order to cancelled.
  3. Add requireFeature('refunds') to the restaurant cancel path for parity.
  4. Hide the "Batal" button client-side with checkPermission('cancel','Transaction') in addition to the status check.
High RBAC-03 Payment gateway cancel/refund endpoints have no authorize() check

Area: Backend   modules/payment-getway/routes/payment.routes.js

router.use(authenticate);
...
router.post('/cancel/:transactionNumber', paymentController.cancelPayment);
router.post('/refund/:transactionNumber', paymentController.refundPayment);

Impact: Only requires being logged in — no authorize('update','Payment'), unlike every other payment/billing route in the codebase. The controller does scope by req.user.tenantId (not cross-tenant), but any authenticated user in the tenant — waiter, trainer, even a member — could cancel or refund a Midtrans payment.

Fix: Add authorize('update', 'Payment') to both routes, and register them in ROUTE_TO_SUBJECT_MAP for consistency.

Medium RBAC-04 normalizeResourcePermissions escalates any "*" grant to full access

Area: Backend   utils/permissionUtils.js:80-83   Proven by test.

if (resource === FULL_ACCESS_RESOURCE) {
  normalized[resource] = [FULL_ACCESS_ACTION];   // ignores rawActions entirely
  continue;
}

Impact: A role configured with resources: { "*": ["read"] } — intended as "read-only access to everything" — silently becomes { "*": ["*"] } (full CRUD on everything). Confirmed by test:

normalizeResourcePermissions({ '*': ['read'] })
// => { '*': ['*'] }   (should be { '*': ['read'] })

No current UI path sets this today, so it's latent — but a landmine for any future "read-only super role" or manually-edited Role.permissions JSON.

Fix: normalized[resource] = normalizeActionList(rawActions); instead of hard-coding the wildcard. Regression test already added.

Medium RBAC-05 autoAuthorize can never match real requests (dead protection)

Area: Backend   middlewares/autoAuthorizeMiddleware.js   used in transaction.routes.js staffAttendance.routes.js   Proven by test.

function autoAuthorize(req, res, next) {
  ...
  const mapping = findRouteMapping(req.path, req.method);
  if (!mapping) {
    // Route not in the map — log in dev, allow through
    return next();
  }
  ...

Impact: ROUTE_TO_SUBJECT_MAP keys are full paths (e.g. /transactions/statistics), but these two route files call router.use(autoAuthorize) from inside a router already mounted at /transactions — Express strips that prefix before the middleware runs, so req.path is really just /statistics. The map lookup can never succeed, and the middleware silently "allows through" every request. Today this is harmless because both files also apply explicit inline authorize() per route — but the middleware's own docstring claims routes are "automatically protected," which is false, inviting a future unprotected route.

Fix: Reconstruct the full path (req.baseUrl + req.path) before matching, and add a startup assertion that mapped routes resolve — or delete autoAuthorize and standardize on the explicit pattern used everywhere else.

Medium RBAC-06 Frontend route guard only checks permissions for ~4% of pages

Area: Frontend   router/index.js:330-345

if (!isPublic && to.meta?.action && to.meta?.subject) {
  if (!isSuperAdmin) {
    if (!checkPermission(to.meta.action, to.meta.subject)) {
      return { path: '/403', ... }
    }
  }
}

Repo-wide scan: 136 total page components, only 6 define both meta.action and meta.subject (including neither of the two new void-transactions.vue pages).

Impact: For the other ~130 pages, direct URL navigation is blocked only by being logged in, subscription/module gating, and whatever the backend API returns. Menu-based hiding prevents a link from being shown, not a URL from being visited. Fine only if every backend endpoint is airtight — RBAC-01/02/03/05 show it currently isn't.

Fix: Add meta.action/meta.subject to every private page (generate from the same data used for menuKeys); at minimum add it to the two void-transaction pages; consider a CI check that fails on private pages missing all of meta.action/subject/public.

Low RBAC-07 navigation.js action/subject fields are never actually checked

Area: Frontend   navigation/navigation.js composables/core/useNavigation.js

Every nav item declares action/subject (including the two added this session), but filterByModuleAccess() only ever checks item.menuKey and subscription access — it never reads item.action/item.subject. checkPermission/canAccess are used in only 3 files total, and never against a nav item.

Impact: A developer can set action/subject believing it gates visibility, when only menuKey matters — exactly the ambiguity that required 3 files to be hand-edited for the void-transaction menu items this session (see RBAC-14).

Fix: Either wire filterByModuleAccess to also call checkPermission(item.action, item.subject), or delete the fields to remove the ambiguity.

Low RBAC-08 No component ever hides a button based on granular permission

Area: Frontend

checkPermission/canAccess/hasMenuAccess are used in exactly 3 files total (router/index.js, their own definitions, useNavigation.js). No .vue component imports them to conditionally render a create/edit/delete button.

Impact: Once a page is reachable (nearly unconditional per RBAC-06), every button on it renders regardless of role, e.g. a waiter sees the exact same "Batal" button as a manager. Backend is the only real gate — fine only when the backend is airtight (it isn't always, per RBAC-01/02/03). Also a poor UX: users click things that then 403.

Fix: Add a small reusable <PermissionGate> component or v-permission directive built on checkPermission; use it for destructive actions, starting with VoidTransactionPanel.vue.

Low RBAC-09 Legacy placeholder module routes have no authorize() at all

Area: Backend   routes/gym/pos.routes.js routes/gym/restaurant.routes.js (mounted at /modules/pos, /modules/restaurant)

router.use(authenticate);
router.use(requireModule(MODULE_NAME));
// no authorize() anywhere in either file

Impact: Low today — every route just returns static placeholder JSON ("implementation coming in Fase 2") — but these are real, mounted, reachable routes with no RBAC pattern to copy. If "finished" later without adding authorize(), real endpoints would ship unprotected.

Fix: Delete the dead placeholders (the real, fully-implemented restaurant module already exists elsewhere), or add authorize() now.

Low RBAC-10 Several default roles fail their own /auth/profile check

Area: Backend   routes/core/auth/auth.routes.js:32 utils/defaultRolePermissions.js   Proven by test.

router.get('/profile', authenticate, authorize('read', 'User'), ...);

cashier, trainer, kitchen, waiter, and staff have no User entry in defaultRolePermissions.js, so can(user, 'read', 'User') is false for them by default — confirmed by test.

Impact: None currently (the frontend never calls this endpoint), but it's a landmine for the next person who wires it up or any tenant that customizes these roles.

Fix: Give every default role baseline User:['read'], or special-case "read your own user record" so it doesn't depend on the generic User permission.

Low RBAC-11 Zero RBAC test coverage; backend suite currently broken; no frontend tests

Area: Both

  • No pre-existing test references rbac.js, permissionUtils.js, autoAuthorizeMiddleware.js, or menuKeys.js.
  • npm test in packages/backend currently fails for every suite (including pre-existing ones) — NODE_ENV=test has no matching DB dialect/.env.test.
  • packages/frontend/package.json has no test script and no vitest/jest dependency at all.

Impact: Bugs like RBAC-04/05 (confirmed via new tests in this audit) could ship silently.

Fix: Fix the backend test env (.env.test or a DB-optional setup hook), land rbacAudit.test.js permanently, add vitest to the frontend and cover usePermissions.js, wire both into CI.

Info RBAC-12 CORS reflects the request origin even when not allow-listed

Area: Adjacent to RBAC   app.js:55-59

if (allowedOrigins.includes(origin) || process.env.NODE_ENV === 'development') {
  callback(null, origin);

Both branches reflect the origin — the allow-list check has no effect, and credentials: true is set. Worth tightening: a stolen/XSS'd token becomes easier to use cross-origin.

Info RBAC-13 Weak hardcoded JWT_SECRET fallback

Area: Backend   utils/jwt.js:4

const JWT_SECRET = process.env.JWT_SECRET || 'supersecret';

If a deployment forgets to set JWT_SECRET, every token (including role/tenant claims) can be forged with a well-known default. Recommend failing fast at boot instead of silently falling back, at minimum for NODE_ENV=production.

Medium RBAC-14 Menu-key ↔ permission wiring is manually duplicated across 3 files

Area: Both   frontend/navigation/menuKeys.js frontend/navigation/menuKeyUtils.js backend/utils/menuKeys.js

Impact: Adding the two void-transactions menu keys this session required hand-editing three separate role→menuKey allow-lists to stay in sync, with no shared source of truth and no test asserting they stay consistent. A missed file silently breaks menu visibility or the SUBJECT_MENU_MAP fallback, and none of the three files import from each other so drift is easy to miss in review.

Fix: Generate the frontend copies from the backend's data at build time, or move both into a shared module. At minimum, add a CI script that diffs the three lists and fails on divergence.

5. Best Practices — How To Fix What Was Found (Action Plan)

  1. RBAC-01 (Critical) — Add tenantId to Roles, scope every role controller query by tenant, block tenant admins from editing global/system-default roles.
  2. RBAC-02 (High) — Add a distinct cancel action for Transaction; restrict to admin/owner/manager by default; enforce on both Gym and Restaurant void paths; mirror client-side.
  3. RBAC-03 (High) — Add authorize('update','Payment') to the two payment routes.
  4. RBAC-04 (Medium) — One-line fix in normalizeResourcePermissions; keep the regression test.
  5. RBAC-05 (Medium) — Fix path matching in autoAuthorize, or delete it and its misleading docstring.
  6. RBAC-06 (Medium) — Backfill meta.action/meta.subject on private pages, starting with financially-sensitive ones.
  7. RBAC-14 (Medium) — Generate/derive menu-key lists instead of hand-syncing 3 files; add a CI consistency check.
  8. RBAC-07/08 (Low) — Wire or delete unused action/subject nav fields; add a <PermissionGate> pattern for destructive buttons.
  9. RBAC-09/10 (Low) — Add authorize() to placeholders or delete them; give roles baseline profile-read access.
  10. RBAC-11 (Low, unblocks everything above) — Fix the backend test environment, land the new RBAC test file, add frontend unit tests, wire both into CI.
  11. RBAC-12/13 (Info) — Tighten CORS allow-list enforcement; require JWT_SECRET in production.

6. Best Practices — How To Implement RBAC Correctly Going Forward

6.1 Backend

  1. One source of truth for "what can call what." Either make autoAuthorize real and load-bearing, or delete it and standardize on the explicit authorize(action, subject) pattern already used almost everywhere. Never keep a real and a fake enforcement path side by side.
  2. Multi-tenancy is a permission dimension, not an afterthought. Any per-tenant-customizable model (roles, printer settings, templates...) needs a tenantId column, and every query needs WHERE tenantId = ... — even on "admin" endpoints. isTenantAdmin() should only ever grant access within the acting user's own tenant.
  3. Separate "routine write" from "destructive/financial correction." Model these as distinct actions so role defaults can differ meaningfully — if it needs a manager's sign-off in real life, it needs a distinct permission in code.
  4. Fail closed, not open. Never write a middleware that defaults to "allow" when it can't find a match.
  5. No hardcoded secret fallbacks. Fail fast at boot if JWT_SECRET is unset outside development.
  6. Test the permission engine like business logic. Pure functions don't need a database — unit test them directly.
  7. Audit-log every permission/role mutation, flagging cross-tenant or global-role changes specifically.

6.2 Frontend

  1. Turn the router guard's UX on everywhere. Set meta.action/meta.subject on every private page, ideally generated from the same source as menuKeys.
  2. One mechanism per concern. Don't keep two systems that look like they both gate the same thing when only one does.
  3. Gate destructive UI at the component level. Use the existing checkPermission composable via a small reusable wrapper/directive.
  4. Keep cached permission data fresh. Invalidate the cached permissions quickly after a backend role change.
  5. Single source of truth for menu keys — generate the frontend copy from the backend's instead of hand-syncing.
  6. Write tests for usePermissions.js and the router guard's permission branch — cheap, pure, and exactly where this audit found drift.

6.3 Checklist For Every New Protected Feature

  • Backend route wrapped in authenticate + authorize(action, subject) (use a specific action like cancel/refund for destructive/financial operations).
  • Route added to ROUTE_TO_SUBJECT_MAP for documentation/tooling, even if autoAuthorize isn't relied upon.
  • subject added to defaultRolePermissions.js for every role that should have access — and explicitly absent from roles that shouldn't.
  • Menu key added to menuKeys.js (frontend and backend) and SUBJECT_MENU_MAP if applicable — verified with a diff.
  • Frontend page's <route> block sets meta.action + meta.subject matching the backend check.
  • Destructive buttons wrapped in a client-side checkPermission(...) check in addition to the status/business-rule check.
  • Cross-tenant test: a user from Tenant B cannot read/mutate Tenant A's data via this route, even with a matching role.
  • Unit test for new pure permission logic; at least one integration test hitting the route as authorized and unauthorized roles.
